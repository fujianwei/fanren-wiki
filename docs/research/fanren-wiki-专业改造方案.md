# fanren-wiki 专业改造方案

> 文档定位：基于 1in8b 正式网站 20 局样本分析与 fanren-wiki 当前代码，给出可执行的产品与工程改造方案。  
> 不含个人汇报、面试包装或泛化业务价值描述。  
> 对比依据：`reports/fanren-wiki-comparison-matrix.md`；正式样本依据：`reports/1in8b-official-20-report.md`。

## 一、结论先行

### 1in8b 值得学习的不是题材，而是机制结构

1in8b 的有效闭环是：

```text
随机出生
→ 年度重心
→ 有条件事件
→ 关键抉择
→ 状态与关系变化
→ 延迟回响
→ 死亡
→ 组合总结
→ 重玩
```

fanren-wiki 当前已经具备：

- 修仙题材；
- 灵根与境界成长；
- 事件、闭关、战斗、灵市；
- 六类结束原因；
- 已接入的 18 条三段命运线；
- 八轴叙事状态；
- 选择记忆与组合结局总结。

当前真正缺的是：

1. 时间层；
2. 关系层；
3. 事件条件层；
4. 可保存、可回看的完整生平；
5. 重玩收集层。

### 不应照搬 1in8b

以下内容不建议直接复制：

- 真实世界人口统计与出生国家对照；
- 现代职业、婚育、房产、金融资产生命周期；
- 健康/幸福/知识/人际关系四维属性；
- 每日真实世界主题；
- 现代追思馆与付费纪念品。

本案应迁移的是机制原则，不是界面和题材。

## 二、目标产品形态

### 1. 单局核心循环

```text
选择阶段重心
→ 推进若干年
→ 自动结算修炼/寿元/伤势/关系
→ 触发 0–2 个候选事件
→ 玩家处理事件
→ 写入选择记忆与长期状态
→ 检查突破、死亡、命运线阶段
→ 进入下一阶段
```

### 2. 阶段而非逐年

修仙题材适合“阶段制”，不一定要逐年点击：

- 炼气期：5 年一个阶段；
- 筑基期：10 年一个阶段；
- 结丹期：20 年一个阶段；
- 元婴期：40 年一个阶段；
- 化神期：80 年一个阶段。

具体年数可配置，不在代码里写死。

### 3. 阶段重心

首批建议提供六类重心：

| 重心 | 主要收益 | 主要代价 |
|---|---|---|
| 苦修 | 修为、突破经验 | 关系疏远、世俗消息滞后 |
| 游历 | 机缘、见识、命运线推进 | 风险、寿元消耗 |
| 丹药/阵法 | 专业能力、物资 | 灵石与时间 |
| 宗门事务 | 地位、人脉 | 私修时间减少 |
| 人情往来 | 关系、忠诚、牵挂 | 修炼效率下降 |
| 养伤/隐居 | 恢复伤势、降低仇怨 | 错过时局与机缘 |

阶段重心的价值不在数值加成，而在**改变下一阶段的事件池与概率**。

### 4. 关系网络

首批只做四类，避免过度设计：

- 师门：师尊、同门；
- 道友：盟友、竞争者、仇敌；
- 亲缘：凡人亲族；
- 道侣/弟子：后期扩展。

每个关系至少包含：

```ts
interface Relation {
  id: string;
  name: string;
  kind: "master" | "peer" | "rival" | "kin" | "companion" | "disciple";
  affinity: number;   // -100 ~ 100
  trust: number;      // 0 ~ 100
  status: "active" | "estranged" | "dead" | "lost";
  lastInteractionTurn: number;
  tags: string[];
}
```

关系需要参与事件条件，例如：

- 有仇敌才触发追杀；
- 有高信任同门才触发护法；
- 亲人年老才触发回乡；
- 道侣关系才触发起双修/分离类后续。

## 三、状态与数据模型改造

### 1. GameState 新增字段

建议新增：

```ts
stage: number
stageFocus: FocusId | null
focusHistory: Array<{ stage: number; focusId: FocusId }>
relations: Record<string, Relation>
timeline: TimelineEntry[]
flags: Record<string, number | boolean | string>
cooldowns: Record<string, number>
```

现有字段继续保留：

- `turn`：事件/阶段推进计数；
- `narrative.threads`：命运线；
- `narrative.axes`：八轴；
- `choiceHistory`：选择记忆；
- `endingSummary`：组合结局。

### 2. TimelineEntry

统一记录事件、选择、关系变化、命运线和死亡：

```ts
interface TimelineEntry {
  id: string;
  stage: number;
  age: number;
  kind: "event" | "choice" | "relation" | "thread" | "breakthrough" | "death";
  title: string;
  text: string;
  eventId?: string;
  threadId?: string;
  relationId?: string;
}
```

用途：

- 结局页完整生平；
- 分享卡；
- 最近人生存档；
- 调试事件链。

### 3. 事件定义扩展

在现有 `GameEvent` 上增加可选条件：

```ts
condition?: {
  minAge?: number;
  maxAge?: number;
  minStage?: number;
  axes?: Partial<Record<NarrativeAxis, { min?: number; max?: number }>>;
  tagsAny?: string[];
  tagsAll?: string[];
  scarsAny?: string[];
  relations?: Array<{ kind: Relation["kind"]; minAffinity?: number; status?: Relation["status"] }>;
  focusAny?: FocusId[];
  flags?: Record<string, boolean | number>;
}
weight?: number;
cooldown?: number;
once?: boolean;
priority?: number;
```

这比继续往页面里写 `if` 更可维护。

## 四、事件触发算法

### 1. 候选池生成

```text
全部事件
→ 按境界过滤
→ 按年龄/阶段过滤
→ 按叙事轴过滤
→ 按标签/伤疤过滤
→ 按关系过滤
→ 按阶段重心过滤
→ 按 flag 过滤
→ 排除 cooldown 内事件
→ 排除 once 已触发事件
```

### 2. 事件排序

建议分三层：

1. **强制事件**：命运线阶段、死亡、突破，优先级最高；
2. **高优先事件**：关系危机、仇敌、宗门大事；
3. **普通事件**：按权重随机。

### 3. 每阶段事件预算

建议每阶段触发：

- 1 个必选事件；
- 0–1 个普通事件；
- 命运线满足条件时替换其中一个普通事件。

这能防止玩家连续读事件，也给阶段重心留下发挥空间。

## 五、阶段结算规则

每次“推进阶段”需要执行固定顺序：

```text
1. 结算寿元
2. 结算修为/修为瓶颈
3. 结算伤势/疾病
4. 结算灵石与资源
5. 结算关系漂移
6. 推进世界/时局
7. 更新事件冷却
8. 生成候选事件
9. 若寿元耗尽/濒死则进入死亡结算
```

结算顺序必须固定并有测试，否则容易出现“先死亡后加修为”“先结局后更新关系”等状态错乱。

## 六、组合结局

### 1. 现有已实现部分

当前已经有：

- 结束原因；
- 三个主轴；
- 命运线落定/断裂/未决；
- 关键记忆；
- 墓志铭；
- 签名。

### 2. 下一阶段补充

结局应继续组合：

- 最高境界；
- 最终寿元；
- 主要关系（道侣/师尊/仇敌/弟子）；
- 已落定/断裂命运线；
- 最大成就与最大代价；
- 修仙纹理；
- 最后一句遗言。

### 3. 修仙纹理建议

不要照搬 1in8b 的“陪伴/工作、根/风、平静/浪潮、今天/明天”，建议建立修仙语义四轴：

| 左轴 | 右轴 | 含义 |
|---|---|---|
| 守道 | 逐势 | 守本心还是顺势而变 |
| 独行 | 结缘 | 独自求道还是经营关系 |
| 慈悲 | 杀伐 | 渡人还是以力破局 |
| 人间 | 天门 | 留恋人间还是追求飞升 |

这四轴可以直接由现有八轴映射，不需要另建状态：

- 守道 ≈ dao + loyalty；
- 逐势 ≈ ambition + guile；
- 独行 ≈ freedom；
- 结缘 ≈ attachment + compassion；
- 慈悲 ≈ compassion；
- 杀伐 ≈ ruthless；
- 人间 ≈ attachment + loyalty；
- 天门 ≈ dao + ambition。

## 七、分阶段实施计划

### 阶段 A：冻结现有改造，建立工程基线

**状态**：当前命运线第一版已完成。

需要完成：

- 保留 18 条命运线与组合结局；
- 不改出生火焰、文案和现有修仙视觉；
- 提交前由用户审查，不自动 commit/push；
- 为当前代码建立可对比基线。

**验收**：

- 61 项测试继续通过；
- 生产构建通过；
- 命运线三段、落定与组合结局可复现。

### 阶段 B：阶段时钟 + 阶段重心

**目标**：解决“只能点事件、没有时间感”。

任务：

1. 新增 `stage`、`stageFocus`、`focusHistory`；
2. 新增阶段推进 action；
3. 新增阶段结算函数；
4. 新增阶段重心选择 UI；
5. 让重心改变事件池权重；
6. 结局页展示阶段经历与主要重心。

**验收**：

- 每局至少经历 8 个阶段；
- 阶段推进不跳步、不重复结算；
- 重心实际改变事件出现概率；
- 寿元耗尽仍在正确时点触发死亡。

### 阶段 C：关系网络

**目标**：让“人”成为长期状态，而不是一次性事件文案。

任务：

1. 新增 `relations`；
2. 新增关系事件效果；
3. 新增关系随阶段漂移；
4. 命运线可以读写关系；
5. 结局页展示主要关系终态。

**验收**：

- 至少 4 类关系可生成；
- 关系状态可影响事件筛选；
- 关系变化能出现在时间线与结局；
- 不会出现已死亡关系继续触发互动。

### 阶段 D：条件事件池

**目标**：让同一事件在不同人生中呈现不同版本。

任务：

1. 扩展事件条件类型；
2. 新建事件筛选/权重服务；
3. 对现有事件补条件；
4. 加入 `once`、`cooldown`、`priority`；
5. 增加调试面板或开发模式日志。

**验收**：

- 高慈悲与高杀伐玩家看到明显不同事件；
- 命运线阶段拥有最高优先级；
- 普通事件不连续重复；
- 事件池不足时有安全兜底。

### 阶段 E：完整生平与重玩存档

**目标**：把单局结果变成可回看、可比较的记忆。

任务：

1. 新增 `timeline`；
2. 结局页增加完整生平；
3. 使用版本化 `localStorage` 保存最近 10 局；
4. 增加“前世纪录”；
5. 增加命运线图鉴与结局谱系；
6. 增加本局分享卡。

**验收**：

- 刷新后仍可回看最近人生；
- 结局数据结构可版本迁移；
- 历史记录不会影响新局状态；
- 用户可以重新打开旧局总结。

### 阶段 F：平衡与内容验收

任务：

- 自动模拟 1000 局，统计境界、死因、命运线落定率和结局分布；
- 检查某条命运线是否长期无法触发；
- 检查事件重复率；
- 检查自动结算死循环与状态爆炸；
- 浏览器验收桌面与移动端。

**验收指标**：

- 每条命运线至少可在自动模拟中触发；
- 无单条结局占比超过 40%；
- 无 10 局连续相同主轴；
- 无负寿元、负资源、重复死亡或空结局；
- 控制台无 error/warning。

## 九、风险与控制

### 风险 1：机制过重

**控制**：阶段重心只做 6 类，关系只做 4 类，首版不引入地图、宗门经营和复杂战斗联动。

### 风险 2：事件条件爆炸

**控制**：先做 5 个通用条件能力，不按每条事件写专用代码。

### 风险 3：数值与叙事脱节

**控制**：所有关键选择必须同时写入 `timeline` 与 `narrative`，不能只改数值。

### 风险 4：结局重复

**控制**：结局由主轴、关系、命运线、境界和结束原因组合，并做自动模拟分布检查。

### 风险 5：旧存档不兼容

**控制**：存档带 `schemaVersion`，加载失败时保留原文并安全降级，不直接覆盖。

## 十、推荐执行顺序

1. 先冻结当前命运线第一版，完成一次用户审查。
2. 做阶段时钟与阶段重心。
3. 做关系系统。
4. 再接条件事件池。
5. 最后做完整生平、历史存档和分享卡。
6. 用自动模拟校准平衡，再做浏览器验收。

不要先扩写更多事件。当前瓶颈是状态结构与反馈链路，不是内容数量。

## 十一、当前可直接确认的判断

- 专业对比已经存在，核心结论可用：`reports/fanren-wiki-comparison-matrix.md`。
- 专业改造边界已经明确：保留修仙视觉，迁移状态机、关系、事件条件和组合终局，不照搬真实人生统计。
- 下一项代码工作应是 **P0 阶段时钟 + 阶段重心**，不是继续增加随机事件。
- 关系系统紧随其后，否则“命运线”仍会停留在标签与文本层。
