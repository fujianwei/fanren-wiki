# RPC 基本原理

## 什么是 RPC

Remote Procedure Call，远程过程调用。让调用远程服务像调用本地方法一样透明，屏蔽网络通信细节。

## 调用流程

```
调用方（Client）                              服务方（Server）
    │                                             │
    │  1. 调用本地 Stub 方法                        │
    │  2. 序列化请求参数                             │
    │  3. 网络传输（TCP/HTTP）  ──────────────────> │
    │                                         4. 反序列化请求
    │                                         5. 反射调用实际方法
    │                                         6. 序列化返回结果
    │  9. 返回结果给调用方      <────────────────── │
    │  8. 反序列化响应                              │
```

核心步骤：
1. **动态代理**：客户端调用接口，框架生成代理对象拦截调用
2. **序列化**：将方法名、参数等对象转为字节流（JSON / Protobuf / Thrift 二进制等）
3. **网络传输**：通过 TCP 长连接发送请求，等待响应
4. **反序列化**：服务端还原请求，执行方法后将结果序列化返回
5. **服务发现**：客户端通过注册中心（ZooKeeper / Nacos）找到服务地址

|节点|角色说明|
|---|---|
|Consumer|需要调用远程服务的服务消费方|
|Registry|注册中心|
|Provider|服务提供方|
|Container|服务运行的容器|
|Monitor|监控中心|

首先服务提供者 Provider 启动然后向注册中心注册自己所能提供的服务。

服务消费者 Consumer 启动向注册中心订阅自己所需的服务。然后注册中心将提供者元信息通知给 Consumer， 之后 Consumer 因为已经从注册中心获取提供者的地址，因此可以通过负载均衡选择一个 Provider 直接调用 。

之后服务提供方元数据变更的话注册中心会把变更推送给服务消费者。

服务提供者和消费者都会在内存中记录着调用的次数和时间，然后定时的发送统计数据到监控中心。


## 核心组件

| 组件 | 作用 |
|------|------|
| 动态代理 | 屏蔽网络调用细节，让调用透明 |
| 序列化协议 | 对象 ↔ 字节流，影响性能和兼容性 |
| 网络传输 | 通常基于 TCP 长连接，减少连接开销 |
| 注册中心 | 服务注册与发现，解耦调用方和服务方 |
| 负载均衡 | 多实例时选择目标节点（轮询/随机/一致性Hash） |

## 序列化协议对比

| 协议 | 优点 | 缺点 |
|------|------|------|
| JSON | 可读性好，兼容性强 | 体积大，性能差 |
| Protobuf | 体积小，性能高 | 需要预定义 schema |
| Thrift | 支持多语言，性能好 | 需要预定义 IDL |

## 常见框架

- **Thrift**：Facebook 开源，美团内部广泛使用，基于 IDL 定义接口
- **gRPC**：Google 开源，基于 HTTP/2 + Protobuf
- **Dubbo**：阿里开源，Java 生态，服务治理能力强
