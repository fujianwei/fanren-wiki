# 缓存与数据库一致性

## 问题背景

数据库数据更新了，缓存还是旧值，用户读到脏数据。本质是两个存储系统（MySQL + Redis）之间的数据同步问题。

---

## 删除 vs 更新缓存

推荐**删除缓存**，原因：

**更新缓存的问题：**
```
问题1：浪费资源
更新数据库 → 立即更新缓存
但这个 key 之后很久没人访问 → 白白计算写入了

问题2：并发覆盖
线程A：写数据库10 → 准备写缓存
线程B：写数据库20 → 先写缓存=20
线程A：后写缓存=10 ← 覆盖了B
最终：数据库=20，缓存=10，不一致
```

删除缓存：等有人访问时再重建，按需加载，没有覆盖问题。

---

## 先删缓存 vs 先更新数据库

**先删缓存，再更新数据库（不推荐）：**
```
线程A：删缓存 → 更新数据库（还没完成）
线程B：查缓存 miss → 读数据库旧值 → 写回缓存
线程A：数据库更新完成
最终：数据库=新值，缓存=旧值，不一致
```
根本原因：删缓存和写数据库之间有窗口期，并发读会把旧值写回缓存。

**先更新数据库，再删缓存（推荐）：**
```
线程A：更新数据库 → 删缓存
线程B：查缓存 miss → 读数据库新值 → 写回缓存
最终一致
```

---

## 删缓存失败怎么办

```
更新数据库成功 → 删缓存失败（网络抖动）
→ 缓存一直是旧值，长期不一致
```

**方案一：MQ 重试**
```
删缓存失败 → 发消息到 MQ → 消费者异步重试删除，直到成功
```

**方案二：Binlog 监听**
```
Canal 等工具订阅 MySQL Binlog
数据库有变更 → 自动触发删缓存
不依赖业务代码，更可靠
```

---

## 延迟双删

先删缓存再更新数据库方案的补偿手段：
```
1. 删缓存
2. 更新数据库
3. 延迟500ms
4. 再删一次缓存（清掉窗口期内写回的旧值）
```
缺点：延迟时间难定，第二次删除也可能失败，窗口期内仍不一致。**不推荐作为主方案。**

---

## 总结

```
操作缓存：删除，不要更新
操作顺序：先更新数据库，再删缓存
删除失败：MQ重试 或 Binlog监听
延迟双删：补偿手段，不是银弹
```
