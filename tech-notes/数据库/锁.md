# 锁

## 锁的分类

```
按粒度：
  表锁：锁整张表，并发度低，MyISAM 用
  行锁：锁具体行，并发度高，InnoDB 用

按模式：
  共享锁 S锁（读锁）：SELECT ... LOCK IN SHARE MODE
    → 允许其他事务也加 S 锁，不允许加 X 锁
  排他锁 X锁（写锁）：SELECT ... FOR UPDATE / UPDATE / DELETE
    → 不允许其他事务加任何锁
```

---

## 行锁

**UPDATE 执行时，InnoDB 对扫描到的行加 X 锁，锁在事务 commit/rollback 后才释放。**

```
三种情况：

命中唯一索引 + 等值查询 → 只锁一行（最优，并发性能最好）
命中普通索引或范围查询 → 行锁 + 间隙锁
不走索引               → 近似全表锁（生产事故高发区，务必避免）
```

**锁的生命周期：**
```
事务开始
  ↓
执行 UPDATE → 加 X 行锁
  ↓
继续执行事务中其他语句（锁持续持有）
  ↓
commit / rollback → 行锁释放
```

行锁不是 UPDATE 执行完就释放，而是等整个事务结束。事务越长，锁持有时间越长，并发冲突越多。

**关于 updateRows == 0：**
```
updateRows == 0 不代表完全没有加锁
InnoDB 是在索引定位阶段加行锁，之后才检查其他 WHERE 条件
如果 WHERE 条件不满足，只是更新了 0 行
RC 隔离级别下一般会提前释放不满足条件的锁
```

## 间隙锁（Gap Lock）

**幻读问题：**
```
事务A                              事务B
BEGIN;
SELECT * WHERE age > 18;
-- 返回 3 行
                                   INSERT (age=20); COMMIT;
SELECT * WHERE age > 18;
-- 返回 4 行  ← 幻读！
```

行锁只锁已存在的行，对新 INSERT 的行无效，防不住幻读。

**间隙锁的作用：锁住索引记录之间的"空间"，阻止其他事务在该范围内 INSERT。**

```
假设索引上有值 100, 200, 300：

执行：SELECT ... WHERE promotion_id BETWEEN 100 AND 300 FOR UPDATE

索引：  100          200          300
         |←-- gap --→|←-- row --→|←-- gap --→|
                   🔒           🔒

行锁：锁住 promotion_id = 200
间隙锁：锁住 (100, 200) 和 (200, 300) 两段空间

其他事务 INSERT promotion_id = 150 或 250 → 阻塞等待，幻读被防住
```

**什么时候加间隙锁：**
```
隔离级别 REPEATABLE READ（MySQL 默认）    → 加间隙锁
隔离级别 READ COMMITTED                  → 不加（只有行锁，放弃幻读保护换并发）
唯一索引等值查询（精确命中一行）           → 不加（唯一索引保证不会有间隙问题）
普通索引 / 范围查询                       → 加间隙锁
```

间隙锁会阻塞合理的 INSERT，降低并发度。高并发系统选择 RC 隔离级别的原因之一。

## 临键锁（Next-Key Lock）

InnoDB 实际使用的是行锁 + 间隙锁的组合，叫临键锁，区间为左开右闭：

```
索引值：10, 20, 30

临键锁区间：
  (-∞, 10]
  (10, 20]
  (20, 30]
  (30, +∞)  ← supremum 锁
```

**临键锁 = 行锁 + 间隙锁，是 InnoDB 默认的行锁实现。**

## 意向锁

```
问题：事务A 锁了表里某几行（行锁），事务B 想加表锁
      事务B 需要逐行检查有没有行锁 → 效率极低

解决：意向锁（表级别）
  事务加行锁前，先在表上加意向锁
  事务B 只需检查表上有没有意向锁，不用逐行扫描

IX（意向排他锁）：准备加行级 X 锁
IS（意向共享锁）：准备加行级 S 锁
```

## 死锁

**成因：循环等待**
```
场景：同一张订单里有两个促销的库存需要扣减

线程1 的处理顺序：A(promotionId=100) → B(promotionId=200)
线程2 的处理顺序：B(promotionId=200) → A(promotionId=100)

T1: 线程1 锁住 A
T2: 线程2 锁住 B
T3: 线程1 等待 B（被线程2持有）
T4: 线程2 等待 A（被线程1持有）
→ 互相等待 → 死锁
```

**MySQL 自动检测死锁：** 发现死锁 → 选择回滚代价小的事务 → 另一个事务继续执行。

**预防死锁：**
```
1. 固定加锁顺序：所有线程按相同顺序（promotionId↑ + skuId↑）申请锁
   → 不可能出现循环等待

   线程1 排序后：A(100) → B(200)
   线程2 排序后：A(100) → B(200)
   → 串行等待，无循环，无死锁

2. 缩短事务：减少锁持有时间，降低冲突概率

3. 降低隔离级别到 RC：去掉间隙锁，减少锁范围
```

**代码示例（按 promotionId + skuId 排序）：**
```java
public static final Comparator<PromotionSkuStockChange> PROMOTION_SKU_STOCK_VO_COMPARATOR =
    (o1, o2) -> {
        if (o1.getPromotionId().equals(o2.getPromotionId())) {
            return o1.getSkuId().compareTo(o2.getSkuId());
        }
        return o1.getPromotionId().compareTo(o2.getPromotionId());
    };
```

## 乐观锁 vs 悲观锁

**悲观锁（Pessimistic Lock）：假设冲突一定发生，先加锁再操作。**
```sql
-- 先锁住行，再读、判断、更新
SELECT * FROM t WHERE id = 1 FOR UPDATE;
-- ... 业务逻辑 ...
UPDATE t SET stock = stock - 1 WHERE id = 1;
```
- 优点：冲突时不浪费无效 UPDATE
- 缺点：锁持有时间长（从 SELECT 到 commit），并发度低

**乐观锁（Optimistic Lock）：假设冲突很少，不加锁，用 WHERE 条件保证正确性。**
```sql
-- 把"数据未被修改"的条件写进 WHERE
UPDATE t SET stock = stock - 1
WHERE id = 1 AND stock >= 1;
-- updateRows=1 → 成功；updateRows=0 → 冲突失败
```
- 优点：无显式锁，并发度高，事务极短
- 缺点：冲突多时大量失败，需重试

**库存扣减用的是乐观锁：**
```sql
UPDATE promotion_sku_stock_used
SET day_stock_used = day_stock_used + #{count}
WHERE promotion_id = #{promotionId} AND poi_id = #{poiId} AND sku_id = #{skuId}
  AND day_stock_used  <= (配置上限 - 购买量)
  AND total_stock_used <= (配置上限 - 购买量)

-- updateRows=1 → 扣减成功
-- updateRows=0 → 库存不足，直接返回失败（不重试，防超卖）
```

- `(poi_id, promotion_id, sku_id)` 是唯一索引，等值查询 → 只锁一行
- 每个操作套独立的 `@Transactional(timeout=1s)`，事务极短，行锁几乎立即释放
