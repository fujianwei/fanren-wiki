# MySQL 为什么使用 B+ 树

## B+ 树的结构特点

- 只有叶子节点存储数据，内部节点只存索引键
- 叶子节点之间通过双向链表相连
- 所有查询都必须到达叶子节点

## B+ 树结构示意

```
                    [30 | 60]                          <- 根节点（只存键）
                   /    |    \
          [10|20]      [40|50]      [70|80]            <- 内部节点（只存键）
          /  |  \       /  |  \      /  |  \

[1|5|9]->[10|15|19]->[20|25|29]->[30|35|39]->[40|45|49]->[50|55|59]->[60|65|69]->[70|75|79]->[80|85|90]
                                                        <- 叶子节点，双向链表相连，存实际数据
```

**N 个键 → N+1 个子节点**：根节点 `[30|60]` 有 2 个键，将数据划分为 3 个区间：
- `< 30` → 左子节点
- `30 ~ 60` → 中子节点
- `> 60` → 右子节点

就像一把尺子上有 2 个刻度，把线段分成 3 段。

**查找 40**：根节点 `30<40<60` 走中间 → `[40|50]` → 命中 40 → 叶子取数据

**范围查询 40~65**：找到叶子 40 → 顺链表右扫 → 45 → 49 → 50 → ... → 65 停止，无需回溯

## 对比其他数据结构

### vs 二叉搜索树 / 红黑树
- 树高太高，百万数据需要约20层，每层一次磁盘 IO，代价极大
- B+ 树每个节点存多个键，树高通常只有 3-4 层，千万数据只需 3 次 IO

### vs B 树
- B 树内部节点也存数据，导致每个节点能存的键更少，树更高
- B 树不支持高效范围查询，需要中序遍历回溯；B+ 树叶子链表直接顺序扫描
- B+ 树所有查询路径等长，性能稳定

### vs Hash 索引
- Hash 只支持等值查询，不支持范围查询、排序、前缀匹配
- B+ 树全部支持

## 为什么 B+ 树层级少

核心原因是**节点扇出（fanout）极大**。

InnoDB 页大小 16KB，内部节点只存键（bigint 8字节 + 指针 6字节 = 14字节），单节点可存：

```
16KB / 14B ≈ 1170 个键
```

3 层可覆盖的数据量：

```
第1层（根）  ：1 个节点
第2层       ：1170 个节点
第3层（叶子）：1170 × 1170 ≈ 136 万条数据
```

千万级数据 4 层就够了。红黑树每个节点只有 2 个子节点，百万数据需要约 20 层。

**本质：扇出越大，树越矮，IO 越少。**

## B+ 树适合磁盘的核心原因

1. **减少 IO 次数**：节点大小对齐磁盘页（InnoDB 默认 16KB），一次 IO 读一页，节点越大存的键越多，树越矮
2. **顺序读友好**：叶子链表支持范围查询时顺序扫描，利用磁盘预读
3. **内部节点可全量缓存**：内部节点不存数据体积小，MySQL 启动后热点内部节点常驻内存，实际查询通常只需 1 次磁盘 IO

## 一句话总结

B+ 树通过"矮胖"结构减少磁盘 IO，通过叶子链表支持高效范围查询，是专为磁盘存储设计的索引结构。
