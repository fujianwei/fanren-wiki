# 事务与隔离级别

## ACID

```
A 原子性：事务内的操作要么全成功，要么全回滚
C 一致性：事务前后数据满足业务约束（转账总金额不变）
I 隔离性：多个事务并发执行，互不干扰
D 持久性：事务提交后，数据永久保存（写入磁盘）
```

---

## 并发问题

```
脏读：读到其他事务未提交的数据
      事务B修改了数据但未提交，事务A读到了 → B回滚后A读到的是脏数据

不可重复读：同一事务内两次读同一行，结果不同
            事务A第一次读到age=18，事务B修改并提交，事务A第二次读到age=20

幻读：同一事务内两次查询，第二次多出了行
      事务A查 age>18 返回3行，事务B插入一行并提交，事务A再查返回4行
```

---

## 四种隔离级别

```
READ UNCOMMITTED（读未提交）：
  能读到其他事务未提交的数据
  问题：脏读、不可重复读、幻读都有

READ COMMITTED（读已提交）：
  只能读到已提交的数据
  解决：脏读
  问题：不可重复读、幻读

REPEATABLE READ（可重复读）← MySQL 默认：
  同一事务内多次读同一行结果一致
  解决：脏读、不可重复读
  问题：幻读（MySQL 用间隙锁基本解决了）

SERIALIZABLE（串行化）：
  事务串行执行，完全隔离
  解决：所有问题
  代价：性能极差
```

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|----------|------|
| READ UNCOMMITTED | ✅有 | ✅有 | ✅有 |
| READ COMMITTED | ❌无 | ✅有 | ✅有 |
| REPEATABLE READ | ❌无 | ❌无 | ⚠️基本无 |
| SERIALIZABLE | ❌无 | ❌无 | ❌无 |

## MVCC（多版本并发控制）

RR 级别下读不加锁，靠 MVCC 实现高并发。

### 三个核心组成

**1. 隐藏字段（每行数据自带）**
```
trx_id：最后一次修改这行的事务ID
roll_pointer：指向 undo log 的指针（历史版本链入口）
```

**2. undo log（版本链）**
```
每次修改一行，旧版本写入 undo log
多次修改形成版本链：

当前版本(trx_id=100) → 旧版本(trx_id=80) → 更旧版本(trx_id=50) → ...
```

**3. ReadView（快照）**
```
事务开始时生成，记录：
  - 当前活跃事务ID列表（未提交的）
  - 最小活跃事务ID
  - 下一个待分配事务ID

读一行时判断：
  trx_id < 最小活跃ID  → 已提交，直接读这个版本
  trx_id 在活跃列表里  → 未提交，找版本链上一个
  trx_id > 最大ID      → 快照后才开始的事务，找版本链上一个

后两种本质一样：这个版本不该看到，沿版本链往前找，直到找到可读的版本。
```

### RC 和 RR 的区别

```
RC（读已提交）：每次 SELECT 都生成新 ReadView
  → 能读到其他事务新提交的数据 → 不可重复读

RR（可重复读）：事务第一次 SELECT 时生成，之后复用
  → 整个事务看到的快照固定 → 可重复读
```

**结果：读操作不加锁，写操作不阻塞读，并发性能高。**

### 设计思想

MVCC 本质是**版本控制 + 快照隔离**，用空间换时间：
```
不加锁，而是保留历史版本
读操作看"过去的快照"，写操作创建"新版本"
读写互不阻塞
```

类似设计：Git（每次提交是快照）、Redis RDB 的 COW（写时复制）、ES 的 segment（只读快照）。

代价：需要存储历史版本，MySQL 用 purge 线程定期清理过期 undo log。
