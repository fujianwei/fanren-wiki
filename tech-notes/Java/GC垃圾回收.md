# GC 垃圾回收

## 怎么判断对象可以被回收

**引用计数法（Java 不用）：**
```
每个对象记录被引用的次数，引用数为 0 → 可以回收
问题：循环引用无法处理
  A 引用 B，B 引用 A，两者引用数都不为 0，但实际没人用
```

**可达性分析（Java 使用）：**
```
从 GC Roots 出发，沿着引用链往下找
能找到的对象 → 存活
找不到的对象 → 可以回收
```

GC Roots 包括：
```
1. 虚拟机栈中引用的对象（方法里的局部变量）
2. 方法区中静态变量引用的对象
3. 方法区中常量引用的对象
4. 本地方法栈中引用的对象
```

## 垃圾回收算法

**标记-清除：**
```
标记所有可回收对象 → 清除
缺点：产生大量内存碎片，大对象找不到连续空间
```

**标记-复制：**
```
把存活对象复制到另一块空间 → 清空原空间
优点：无碎片
缺点：需要双倍内存
适用：新生代（存活对象少，复制代价小）
```

**标记-整理：**
```
标记存活对象 → 移动到一端 → 清理边界外的内存
优点：无碎片，不需要双倍内存
缺点：移动对象开销大
适用：老年代
```

**分代收集：**
```
新生代：对象存活率低 → 标记-复制（Minor GC）
老年代：对象存活率高 → 标记-整理（Full GC）
```

## 常见垃圾回收器

**新生代：**
```
Serial：          单线程，STW，适合单核小内存
ParNew：          Serial 的多线程版本，配合 CMS 使用
Parallel Scavenge：多线程，注重吞吐量
```

**老年代：**
```
Serial Old：   单线程
Parallel Old： 多线程，注重吞吐量
CMS：          并发标记清除，停顿时间短，适合对延迟敏感的场景
```

**全能回收器：**
```
G1（JDK9 默认）：
  把堆分成多个 Region，不区分新老年代
  优先回收垃圾最多的 Region
  可预测停顿时间（-XX:MaxGCPauseMillis）
  适合大堆、对停顿时间有要求的场景

ZGC（JDK11+）：
  停顿时间极短（< 10ms）
  适合超大堆（TB级）
```

---

## STW（Stop The World）

GC 时暂停所有业务线程：
```
GC 需要分析对象引用关系
如果业务线程还在跑，引用关系一直在变，分析不准确
→ 必须暂停所有业务线程才能安全 GC
```

STW 时间越长，系统停顿越久，用户感知越明显。**GC 优化的核心目标就是减少 STW 时间。**

---

## Minor GC vs Full GC

```
Minor GC：只回收新生代，频率高，速度快，STW 短
Full GC： 回收整个堆（新生代+老年代），频率低，速度慢，STW 长
```

**触发 Full GC 的场景：**
```
1. 老年代空间不足
2. 方法区空间不足
3. 显式调用 System.gc()（不建议）
4. 空间分配担保失败
```

**Full GC 是性能杀手，优化目标是减少 Full GC 频率。**
