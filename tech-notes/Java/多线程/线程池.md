# 线程池

## 使用示例

```java
public class ThreadPoolDemo {
    public static void main(String[] args) {
        // 声明线程池
        ThreadPoolExecutor executor = new ThreadPoolExecutor(
                2,                             // 核心线程数
                4,                             // 最大线程数
                60,                            // 非核心线程空闲存活时间
                TimeUnit.SECONDS,              // 时间单位
                new ArrayBlockingQueue<>(10),  // 有界队列，容量10
                Executors.defaultThreadFactory(),
                new ThreadPoolExecutor.AbortPolicy()
        );

        // 提交10个任务
        for (int i = 0; i < 10; i++) {
            int taskId = i;
            executor.execute(() -> {  // execute() 提交任务，Lambda 实现 Runnable
                System.out.println("任务" + taskId + " 由线程 "
                        + Thread.currentThread().getName() + " 执行");
            });
        }

        executor.shutdown(); // 等所有任务执行完后关闭线程池
    }
}
```

输出：
```
任务0 由线程 pool-1-thread-1 执行
任务1 由线程 pool-1-thread-2 执行
任务2 由线程 pool-1-thread-1 执行
...
```

---

## 为什么需要线程池

```
每次来一个任务就创建一个线程：
  创建线程有开销（内存分配、OS调度）
  任务完成线程销毁，下次再创建
  → 频繁创建销毁，浪费资源
  → 线程数量不可控，可能创建过多导致 OOM
```

线程池：**提前创建好一批线程，任务来了直接用，用完放回池子复用。**

## 核心参数（7个）

```java
new ThreadPoolExecutor(
    corePoolSize,      // 核心线程数
    maximumPoolSize,   // 最大线程数
    keepAliveTime,     // 非核心线程空闲存活时间
    TimeUnit,          // 时间单位
    workQueue,         // 任务队列
    threadFactory,     // 线程工厂
    rejectedHandler    // 拒绝策略
)
```

**核心线程 vs 非核心线程：**
```
核心线程：常驻线程，即使空闲也不销毁
非核心线程：超过核心线程数时创建，空闲超过 keepAliveTime 就销毁
```

## 任务提交流程

```java
if (当前线程数 < corePoolSize) {
    创建核心线程直接执行任务  // 即使有空闲线程也创建新的
    return;
}
if (队列未满) {
    任务入队
    if (线程池已shutdown) 移除任务并拒绝;
    else if (线程数为0) 创建一个线程; // 保证有线程消费队列
    return;
}
if (当前线程数 < maximumPoolSize) {
    创建非核心线程执行任务
    return;
}
触发拒绝策略
```

关键点：**先填满核心线程 → 再填满队列 → 再创建非核心线程 → 最后拒绝**

**细节：核心线程数以内，每来一个任务就创建一个新线程，即使有空闲线程：**
```
corePoolSize = 5，当前3个线程都空闲
来了新任务 → 不复用空闲线程，直接创建第4个核心线程
原因：尽快把核心线程创建满，后续任务直接复用
```

## 线程复用原理

线程执行完任务后不销毁，循环从队列取下一个任务：

```java
void runWorker() {
    while (task != null || (task = getTask()) != null) {
        task.run();
    }
    // 退出循环 → 线程销毁
}

Task getTask() {
    if (核心线程) {
        return queue.take();  // 永久阻塞等待，不超时不销毁
    } else {
        return queue.poll(keepAliveTime, TimeUnit); // 超时没任务 → 返回null → 线程销毁
    }
}
```

核心线程靠 `queue.take()` 永久阻塞等待，非核心线程靠 `queue.poll()` 超时等待，超时没任务就退出销毁。

## 任务队列类型及对线程池行为的影响

| 队列 | 特点 | 适用场景 |
|------|------|------|
| LinkedBlockingQueue | 无界队列，容量 Integer.MAX_VALUE | 任务量不可控时慎用，可能 OOM |
| ArrayBlockingQueue | 有界队列，容量固定 | 需要限制队列大小，生产推荐 |
| SynchronousQueue | 不存储任务，直接交给线程 | maximumPoolSize 设大，快速响应 |
| PriorityBlockingQueue | 优先级队列 | 任务有优先级 |

**LinkedBlockingQueue（无界队列）：**
```
maximumPoolSize 永远不会生效，队列永远不满，不会创建非核心线程
实际最大并发 = corePoolSize
任务堆积过多 → OOM
Executors.newFixedThreadPool 就用这个，生产慎用
```

**SynchronousQueue：**
```
队列永远是满的（不存任务），任务来了直接创建非核心线程
实际最大并发 = maximumPoolSize
Executors.newCachedThreadPool 用这个，maximumPoolSize=Integer.MAX_VALUE → 可能创建大量线程 → OOM
```

## 四种拒绝策略

**触发时机：当前线程数 = maximumPoolSize 且队列已满，新任务无处安放。**

**AbortPolicy（默认）：**
```
直接抛出 RejectedExecutionException
调用方需要 try-catch 处理，否则任务丢失且程序异常
```
适用：任务不能丢，必须感知到拒绝，由调用方决定怎么处理。

**CallerRunsPolicy：**
```
由提交任务的线程（调用者）自己执行这个任务

降速保护原理：
主线程 execute() → 线程池满了 → 主线程自己执行任务
主线程执行任务期间 → 无法继续提交新任务
→ 提交速度自动降下来，线程池趁机消化积压
→ 主线程执行完 → 继续提交，又满了 → 又自己执行
→ 形成自动限流
```
适用：任务不能丢，可以接受变慢，不想抛异常。

**DiscardPolicy：**
```
直接丢弃新任务，什么都不做，不抛异常
危险点：任务丢了调用方完全不知道，排查问题困难
```
适用：任务允许丢失，比如日志上报、监控打点等非核心任务。

**DiscardOldestPolicy：**
```
丢弃队列头部最老的任务，然后重新尝试提交新任务

队列：[任务1, 任务2, 任务3]（任务1最老）
新任务4来了，线程池满了
→ 丢弃任务1
→ 重新提交任务4 → 入队成功
→ 队列：[任务2, 任务3, 任务4]
```
适用：新任务比老任务更重要，比如实时数据更新，旧数据可以丢。

**自定义拒绝策略（生产推荐）：**
```java
executor.setRejectedExecutionHandler((task, executor) -> {
    log.warn("线程池满了，任务被拒绝：{}", task); // 记录日志
    alertService.send("线程池告警");              // 报警
    taskRepository.save(task);                   // 存库等待重试
});
```

**对比总结：**

| 策略 | 任务会丢吗 | 抛异常吗 | 适用场景 |
|------|------|------|------|
| AbortPolicy | 会 | 会 | 必须感知拒绝，调用方处理 |
| CallerRunsPolicy | 不会 | 不会 | 任务不能丢，可以变慢 |
| DiscardPolicy | 会 | 不会 | 非核心任务，允许丢失 |
| DiscardOldestPolicy | 会（丢老的） | 不会 | 新任务优先级高于老任务 |
| 自定义 | 看实现 | 看实现 | 生产环境推荐 |

## 线程池状态流转

```
RUNNING   → 正常运行，接受新任务，处理队列任务
    ↓ shutdown()
SHUTDOWN  → 不接受新任务，继续处理队列中的任务
    ↓ shutdownNow() 或队列和线程都空了
STOP      → 不接受新任务，不处理队列任务，中断正在执行的线程
    ↓ 所有任务都终止了
TIDYING   → 所有任务终止，线程数为0，准备执行 terminated()
    ↓ terminated() 执行完
TERMINATED → 完全终止
```

**shutdown() vs shutdownNow()：**
```
shutdown()：温柔关闭，等队列里的任务都执行完再关
shutdownNow()：强制关闭，中断所有线程，返回未执行的任务列表
```

## 常见问题

**OOM：**
```
原因1：LinkedBlockingQueue 无界队列，任务堆积
原因2：newCachedThreadPool maximumPoolSize 无限大，创建大量线程
解决：使用有界队列 + 合理的 maximumPoolSize
```

**线程池死锁：**
```
线程池里的任务提交子任务到同一个线程池，等待子任务完成
但线程池满了，子任务进了队列，父任务一直等 → 死锁
解决：父子任务用不同的线程池，或用 ForkJoinPool
```

**任务执行异常被吞掉：**
```
execute() 提交的任务抛异常 → 线程销毁，异常打印但不抛给调用者
submit() 提交的任务抛异常 → 异常封装在 Future 里，get() 时才抛出
解决：
  1. 用 submit() + future.get() 捕获异常
  2. 自定义 ThreadFactory，给线程设置 UncaughtExceptionHandler
```

## 线程池大小怎么设置

```
CPU 密集型任务（计算为主）：
  线程数 = CPU核心数 + 1
  线程一直在用CPU，多了反而增加切换开销

IO 密集型任务（网络/磁盘为主）：
  线程数 = CPU核心数 * 2
  线程经常等待IO，可以多开线程利用等待时间
```

实际生产中需要结合压测结果调整，公式只是起点。
