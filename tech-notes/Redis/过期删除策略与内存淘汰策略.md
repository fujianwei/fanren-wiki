# Redis 过期删除 & 内存淘汰

## 过期删除策略

共有三种策略，Redis 采用其中两种：

**1. 定时删除**
给每个 key 创建定时器，过期时间到了立即删除。
- 优点：内存最友好，过期立即清理
- 缺点：key 数量大时定时器极多，CPU 开销极大
- **Redis 未采用**：单线程模型下大量定时器会严重影响主线程处理请求

**2. 惰性删除**
不主动删，等到访问这个 key 时才检查是否过期，过期了再删。
```
GET key → 检查是否过期 → 过期则删除返回 nil，未过期正常返回
```
- 优点：对 CPU 友好，按需检查
- 缺点：过期 key 如果一直没被访问，一直占着内存

**3. 定期删除**
每隔一段时间，随机抽取一批 key 检查是否过期，删除其中过期的。
```
每隔 100ms → 随机抽 20 个 key → 删除其中过期的
→ 如果过期比例超过 25%，继续抽，直到比例降下来或超时
```
- 优点：定期清理，内存不会一直膨胀
- 缺点：随机抽取，不能保证所有过期 key 都被及时清理

**三种策略对比：**

| 策略 | 内存友好 | CPU 友好 | Redis 是否使用 |
|------|------|------|------|
| 定时删除 | ✅ 立即清理 | ❌ 开销大 | ❌ |
| 惰性删除 | ❌ 可能堆积 | ✅ 按需检查 | ✅ |
| 定期删除 | ✅ 定期清理 | ✅ 控制频率 | ✅ |

**Redis 选择惰性删除 + 定期删除组合**，在 CPU 和内存之间取得平衡：
```
惰性删除：访问时兜底清理
定期删除：后台定期批量清理
```

## 惰性删除细节

**检查时机：**
不是独立后台任务，而是嵌在每个命令的执行流程里：
```
客户端发来 GET key
  ↓
执行命令前调用 expireIfNeeded(key)
  ↓
过期 → 删除 key，返回 nil
未过期 → 正常执行，返回值
```

**主从复制场景：**
从节点不会主动删除过期 key，只等主节点同步 DEL 命令过来才删，原因是从节点只执行主节点同步的命令，不自己做决策，否则主从数据会不一致。

```
主节点：key 过期 → 惰性删除 → 同步 DEL 命令给从节点
从节点：收到 DEL 命令 → 才真正删除

主节点删除之前，从节点读到过期 key：
→ 发现已过期，返回 nil，但不删除，等主节点的 DEL 命令
```

这意味着从节点存在一个窗口期，逻辑上已过期但还未删除，取决于主节点何时触发惰性删除。

## 定期删除细节

**惰性删除 vs 定期删除的本质区别：**
- 惰性删除：针对具体某个 key，有人访问才检查，是**被动的**
- 定期删除：不依赖客户端请求，Redis 自己的后台定时任务，是**主动的**

```
惰性删除：客户端 GET key1 → 才检查 key1，没人访问永远不检查
定期删除：不管有没有客户端请求，每隔一段时间自动触发，随机抽 key 检查
```

**Redis 单线程与事件循环：**

Redis 是单线程，用事件循环不断检查有没有事情要处理，事件循环本身没有固定间隔，尽可能快地循环：

```
while(true) {
    执行 FAST 定期删除

    epoll_wait(1ms)   // 处理客户端请求
    处理所有就绪的客户端请求

    检查定时任务列表，到时间了就执行 → SLOW 定期删除
}
```

**SLOW 定期删除是定时任务**，挂在事件循环里，每次循环检查"到时间了吗"，到了才执行，间隔 100ms（每秒 10 次）。

```
事件循环：不断跑，尽可能快（载体）
定时任务：到时间才执行（乘客，到站下车）
```

即使没有任何客户端请求，事件循环照常运行，定期删除照样触发。

**两种模式：**

| 模式 | 触发时机 | 单次执行上限 | 目的 |
|------|------|------|------|
| FAST | 每次事件循环前 | 1ms | 高频轻量清理 |
| SLOW | 定时任务（默认10次/秒） | 25ms | 低频深度清理 |

**SLOW 模式执行过程：**
```
遍历所有 db（默认16个）
  ↓
每个 db 随机抽 20 个设置了过期时间的 key
  ↓
删除其中已过期的
  ↓
如果过期比例 > 25%，继续抽 20 个，循环执行
  ↓
直到过期比例 < 25% 或执行时间超过 25ms，停止
```

**为什么随机抽取而不是全量扫描？**
Redis 可能有千万级 key，全量扫描会长时间阻塞主线程。随机抽取是在清理效果和 CPU 开销之间的权衡，用概率保证大部分过期 key 最终被清理到。

---

## 两者结合后仍存在的问题

大量 key 集中过期时：
```
定期删除：每次只抽 20 个，来不及全部清理
惰性删除：这些 key 没有被访问，不会触发
  ↓
大量过期 key 堆积，内存持续膨胀
```

这时需要**内存淘汰策略**兜底——当内存超过 maxmemory 限制时，强制淘汰一些 key 释放内存。

---

## 内存淘汰策略

内存超过 `maxmemory` 限制时，新写入请求触发淘汰，强制删除一些 key 释放内存。共 8 种策略：

**不淘汰：**
- `noeviction`：内存满了直接报错，写入失败（默认）

**针对设置了过期时间的 key：**
- `volatile-lru`：淘汰最近最少使用的 key
- `volatile-lfu`：淘汰使用频率最低的 key
- `volatile-random`：随机淘汰
- `volatile-ttl`：淘汰剩余过期时间最短的 key

**针对所有 key：**
- `allkeys-lru`：淘汰最近最少使用的 key
- `allkeys-lfu`：淘汰使用频率最低的 key
- `allkeys-random`：随机淘汰

**LRU vs LFU：**
```
LRU（最近最少使用）：淘汰最久没被访问的
  → 适合热点数据集中、访问有时间局部性的场景

LFU（最低使用频率）：淘汰历史访问次数最少的
  → 适合长期冷数据混在热数据里的场景
  → 比 LRU 更能识别真正的冷数据
```

**生产环境推荐：**
```
缓存场景（允许淘汰）→ allkeys-lru 或 allkeys-lfu
有过期时间的缓存   → volatile-lru
不能丢数据        → noeviction（配合持久化）
```
