# Redis 缓存问题

## 三者对比

|      | 穿透         | 击穿        | 雪崩                    |
| ---- | ---------- | --------- | --------------------- |
| 原因   | 查不存在的数据    | 热点 key 过期 | 大量 key 同时过期或 Redis 宕机 |
| 影响范围 | 单个不存在的 key | 单个热点 key  | 大量 key 或整个缓存层         |
| 解决   | 缓存空值/布隆过滤器 | 互斥锁/逻辑过期  | 随机TTL/高可用/限流降级        |

---

## 缓存穿透

**根本原因**：查的数据根本不存在，缓存永远没有，每次都透过缓存直接打到数据库。

```
正常流程：
请求 → Redis 有 → 直接返回（数据库没压力）

穿透流程：
请求 key=-1 → Redis 没有 → 查数据库 → 数据库也没有 → 返回空
下次再请求 key=-1 → 重复上面流程，每次都打数据库
```

**为什么危险：**
攻击者构造大量不存在的 key（id=-1, id=-2...），每个请求都绕过缓存直接打数据库，数据库扛不住就崩了。

**解决方案：**

方案一：**缓存空值**
```
查数据库没有 → 往 Redis 存 key=-1: null，TTL 设短（比如60秒）
下次请求 key=-1 → Redis 返回 null，不查数据库
```
缺点：攻击者不断换新的不存在的 key，Redis 里存了大量无用空值，浪费内存。

方案二：**布隆过滤器**
```
系统启动时，把所有合法的 key 加载到布隆过滤器
请求进来 → 先问布隆过滤器：这个 key 可能存在吗？
  → 不存在：直接拦截，不查缓存也不查数据库
  → 可能存在：正常走缓存流程
```
布隆过滤器原理：多个 hash 函数对 key 取 hash，映射到 bitmap 的多个位置，全部为 1 才认为可能存在。有一定误判率（认为存在但实际不存在），但不会漏判（实际存在的一定判为存在）。

**bitmap 大小与误判率：**

bitmap 越小，位置越容易被占满，不同 key 的 hash 位置重叠概率越高，误判率越高：
```
bitmap 很小时：
key1 映射到位置 [1, 3, 5]
key2 映射到位置 [1, 3, 7]
查询 key3 映射到 [1, 3, 5] → 全部为1 → 误判为存在
```

根据预期元素数量 n 和可接受误判率 p 计算 bitmap 大小：
```
m = -n * ln(p) / (ln2)²

例：存 1000 万个 key，误判率 0.1%
m ≈ 1000万 * 10 ≈ 1亿 bit ≈ 12MB
```

**12MB 存 1000 万个 key，这正是布隆过滤器的优势**——相比直接存 key，内存极小。

## 缓存击穿

**根本原因**：单个热点 key 过期的瞬间，并发请求全部 miss，同时涌入数据库。

```
平时：
1000 个请求 → Redis 命中热点 key → 直接返回，数据库没压力

热点 key 过期的瞬间：
1000 个请求 → Redis 全部 miss → 1000 个请求同时查数据库
→ 数据库瞬间压力暴增
→ 每个请求都拿到数据，又各自写回 Redis（重复写了999次）
```

**解决方案：**

方案一：**互斥锁**
```
key 过期后，第一个请求拿到锁 → 查数据库 → 写回 Redis → 释放锁
其他请求拿不到锁 → 等待 → 锁释放后直接读 Redis
```
缺点：等待期间请求被阻塞，有延迟。

方案二：**逻辑过期**
```
Redis 不设置真实 TTL，value 里存一个逻辑过期时间：
{data: "xxx", expireTime: 1714000000}

请求进来：
  → 读到数据，检查 expireTime 是否过期
  → 过期了：返回旧数据（不阻塞），同时异步启动线程去更新缓存
  → 没过期：直接返回
```
缺点：过期后短暂返回旧数据，有数据不一致窗口。

## 缓存雪崩

**根本原因**：大量 key 同时过期，或 Redis 宕机，缓存层整体失效，所有请求同时打到数据库。

```
场景一：大量 key 同时过期
系统启动时批量写入缓存，TTL 都设成一样 → 同一时刻全部过期
→ 所有请求同时打数据库 → 数据库崩溃

场景二：Redis 宕机
Redis 挂了 → 所有请求全部打到数据库 → 数据库崩溃
```

**和击穿的区别：**
- 击穿是**单个热点 key** 过期
- 雪崩是**大量 key** 同时过期，或整个 Redis 不可用

**解决方案：**

针对大量 key 同时过期：
```
过期时间加随机值：TTL = 基础时间 + random(0, 300秒)
把集中过期打散，避免同一时刻大量 key 失效
```

针对 Redis 宕机：
```
Redis 高可用：主从复制 + 哨兵自动故障转移，或 Cluster 集群
服务降级限流：数据库压力过大时直接返回默认值，保护数据库
```
