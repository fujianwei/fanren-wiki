# Redis 分布式锁

## 为什么需要分布式锁

单机环境用 synchronized 或 ReentrantLock 就能保证线程安全，但分布式环境下多个服务实例各自的 JVM 锁互不影响：

```
服务A实例1：synchronized 加锁 ✅
服务A实例2：synchronized 加锁 ✅  ← 两个实例同时拿到锁，并发问题没解决
```

需要一个**所有实例共享的锁**，这就是分布式锁。

---

## 基础实现：SET NX + EX

```
SET lock_key unique_value NX EX 30
```

- `NX`：key 不存在才设置，保证只有一个客户端能加锁
- `EX 30`：30秒过期，防止宕机后锁永远不释放
- `unique_value`：每个客户端生成唯一值，释放时验证是自己的锁

**为什么必须设置过期时间？**
过期时间是防死锁的兜底保障，不是正常释放路径：
```
正常情况：业务执行完 → 主动释放锁
异常情况：进程宕机，finally 块没机会执行 → 靠过期时间自动释放
```
永不过期的锁一旦持有者宕机，锁永远无法释放，系统死锁。

**过期时间设多长？**
- 太短：业务没执行完锁就释放了，并发问题
- 太长：宕机后其他线程等待时间太长，系统不可用
- 解决：看门狗机制

---

## 释放锁：Lua 脚本保证原子性

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
end
return 0
```

为什么用 Lua？get 和 del 是两步操作，不是原子的：
```
线程A：get 验证是自己的锁 ✅
线程A：锁恰好过期，被线程B抢走
线程A：del 删掉了线程B的锁 ← 误删
```
Lua 脚本在 Redis 中原子执行，避免误删。

---

## 看门狗机制（解决过期时间问题）

过期时间设短，但只要业务还在跑就自动续期：

```
加锁成功 → 启动后台看门狗线程
看门狗每隔10秒检查：
  → 业务线程还活着 → 给锁续期（重置为30秒）
  → 业务线程结束  → 停止续期，锁自然过期
```

**怎么判断业务还在跑：**
看门狗和业务线程在同一个进程里，同生共死：
```
正常完成：业务执行完 → 主动 del 锁 → 看门狗停止
进程宕机：看门狗也挂了 → 不再续期 → 锁自然过期释放
```

本质就是一个**定时轮询任务**，活着就续期，死了就让锁自然过期。

## Redis vs ZooKeeper 分布式锁

| | Redis | ZooKeeper |
|------|------|------|
| 性能 | 高 | 较低 |
| 可靠性 | 一般 | 高（强一致性） |
| 实现复杂度 | 简单 | 较复杂 |
| 适用场景 | 高并发、允许极小概率失败 | 强一致性要求 |

生产环境推荐直接用 **Redisson**，封装了看门狗等机制，不用自己实现。

## Redlock 算法

**主从架构下的锁丢失问题：**
```
线程A在主节点加锁成功
主节点宕机，锁还没同步到从节点（主从同步是异步的）
从节点升为新主节点（锁不存在了）
线程B在新主节点加锁成功
→ A和B同时持有锁
```
根本原因：锁丢失（主节点宕机导致锁没同步过去）→ 从节点上锁不存在 → 其他线程能加锁成功。

**Redlock 的解决思路：抛弃主从，换成多个完全独立的单节点。**

```
不是主从，不是集群，就是5个独立部署的 Redis 实例：
redis-1: 192.168.1.1
redis-2: 192.168.1.2
redis-3: 192.168.1.3
redis-4: 192.168.1.4
redis-5: 192.168.1.5
互相之间没有任何关系，不存在同步问题
```

**加锁流程：**
```
1. 记录开始时间 t1
2. 依次向全部5个节点请求加锁
3. 记录结束时间 t2
4. 判断是否成功：
   → 超过半数节点（3个）加锁成功
   → 且耗时 t2-t1 < 锁过期时间（保证锁还有足够有效期）
   → 才算加锁成功
5. 释放时向所有节点发送释放命令
```

**为什么超过半数就算成功？**
```
线程A先加锁：拿到节点1、2、3、4、5 → 超过半数，成功
线程B后加锁：节点1、2、3已有锁，最多拿到2个 → 不超过半数，失败

数学上不可能两个线程同时都拿到超过半数的节点
A拿了3个，B最多只剩2个
```

**节点数量为什么是奇数（一般5个）？**
```
3个节点：挂1个还剩2个，凑不够半数，可用性差
5个节点：挂2个还剩3个，仍能正常工作
7个节点：挂3个还剩4个，但成本高，5个够用
奇数避免平票，偶数节点容易出现半数对半数的情况
```

**代价：** 需要单独维护5个独立实例，运维成本高。生产环境大多数场景还是主从+哨兵，接受极小概率的锁丢失风险，业务层做幂等兜底。
