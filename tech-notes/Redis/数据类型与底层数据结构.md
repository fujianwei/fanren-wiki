### Q1：Redis 有哪些数据类型，底层数据结构是什么？

| 类型 | 底层结构 | 使用场景 |
|------|------|------|
| String | SDS（简单动态字符串） | 缓存、计数器、分布式锁 |

### Q2：SDS 相比 C 字符串有什么优势？

- **O(1) 获取长度**：SDS 头部记录 len，C 字符串需要遍历
- **二进制安全**：SDS 以 len 判断结尾，C 字符串以 `\0` 判断，无法存储二进制数据
- **预分配 + 惰性释放**：减少频繁扩容的内存分配次数

## 底层结构：SDS

![[Pasted image 20260422203917.png]]

alloc：通过 `alloc - len` 计算 出剩余的空间大小，判断空间是否足够。不足：自动将 SDS  的空间扩展至执行修改所需的大小，再执行实际的修改操作。使用 SDS 不用手动修改 SDS 的空间大小，也不用担心缓存不够，缓存溢出。
flags：标识sds的不同缓存类型，一共5种：5、8、16、32、64。这 5 种类型的主要**区别就在于，它们数据结构中的 len 和 alloc 成员变量的数据类型不同**。目的是：不同的String，使用不同的类型，有效的节省内存空间。特别小的一个数，就别用64保存了。
buf：字节数组，用来保存实际数据

为什么需要len？因为：由于长度统计变量len的存在，读写字符串时不依赖'\0'终止符，保证了二进制安全。

### Q3：ZSet 为什么用跳表而不用红黑树？

- **范围查询更高效**：跳表按顺序排列，范围查询直接顺序遍历；红黑树需要中序遍历
- **实现简单**：跳表代码复杂度远低于红黑树，便于维护
- **内存占用相近**：跳表通过随机层数控制索引密度，空间效率与红黑树相当
- 两者查找时间复杂度均为 O(logN)，性能差距不大

### Q4：跳表的结构和查找原理？

```
层3：1 ──────────────────────────> 9
层2：1 ──────> 4 ──────────────> 9
层1：1 ──> 2 -> 4 ──> 6 ──> 8 -> 9
```

- 每个节点随机生成层数，上层是下层的"快速通道"
- 查找时从最高层开始，找到比目标大的节点就下降一层，逐步逼近
- 时间复杂度 O(logN)，空间复杂度 O(N)

### Q5：Hash 什么时候从 listpack 升级为 hashtable？

hash类型的结构由紧凑的压缩列表，转换为哈希表。

满足任一条件触发升级：
- 元素数量超过 `hash-max-listpack-entries`（默认 128）
- 任意 value 长度超过 `hash-max-listpack-value`（默认 64 字节）

listpack 是紧凑的连续内存结构，小数据时内存利用率高；数据量大后查找退化为 O(N)，升级为 hashtable 保证 O(1)。

### Q6：Redis 的 hashtable 如何解决哈希冲突？如何扩容？

- **冲突解决**：链地址法，冲突的 key 挂在同一个桶的链表上
- **扩容时机**：负载因子 > 1 时触发（BGSAVE 期间阈值提高到 5，避免影响持久化）
- **渐进式 rehash**：同时维护两张 hashtable（ht[0] 和 ht[1]），每次增删改查时顺带迁移一个桶，避免一次性迁移阻塞（）

渐进式 rehash 步骤如下：
1 给「哈希表 2」 分配空间；
2 在 rehash 进行期间，每次哈希表元素进行新增、删除、查找或者更新操作时，Redis 除了会执行对应的操作之外，还会顺序将「哈希表 1 」中索引位置上的所有 key-value 迁移到「哈希表 2」 上；
3 随着处理客户端发起的哈希表操作请求数量越多，最终会把「哈希表 1 」的所有 key-value 迁移到「哈希表 2」，从而完成 rehash 操作。

和Java的hashmap很像，可以对比记忆。
一、 相似之处（核心数据结构）
1. **数据结构**：都采用“数组 + 链表”存储键值对。
2. **冲突处理**：都使用**链地址法**（Chain Hashing）解决哈希冲突，将冲突节点挂在桶的链表中。
3. **负载因子**：为了保证查询效率，都通过负载因子（Load Factor = 已存元素数 / 桶个数）来控制扩容。

二、 核心不同点（实现细节）

| 特性            | Redis Dict             | Java HashMap                 |
| ------------- | ---------------------- | ---------------------------- |
| **扩容方式**      | **渐进式 Rehash** (分次完成)  | **一次性全量迁移** (阻塞主线程，redis单线程) |
| **节点插入**      | 插入链表**头部**             | 插入链表**尾部** (JDK8+)           |
| **冲突优化**      | 纯链表                    | 链表长 > 8 且容量 > 64 自动**转红黑树**  |
| **触发扩容**      | 负载因子一般 > 1 (高负载时)      | 负载因子 > 0.75                  |
| **rehash 机制** | 同时维护 `ht[0]` 和 `ht[1]` | 新建一个大数组，一次性搬移                |

三、 关键区别点分析
1. **渐进式 Rehash (最核心区别)**
    - **Redis**：作为缓存数据库，数据量可能非常大（百万、千万级）。如果一次性重新计算所有Key的哈希并迁移，会阻塞主线程导致Redis卡死。因此，Redis 在扩容时会同时保留新旧两个哈希表（`ht[0]` 和 `ht[1]`），在后续的每一次数据增删改查时，顺带迁移一部分旧数据，分摊时间复杂度到多次操作中。
    - **Java**：扩容期间主线程暂停，完成全量数据迁移。
2. **哈希冲突的优化**
    - **Java**：JDK 1.8 后的 `HashMap` 引入了红黑树，当链表过长时，查询效率从O(n)变成O(logn) 
    - **Redis**：为了极致的插入效率和简单的内存管理，依然主要依赖链表。为了防止冲突过多，Redis 通过定时任务和定期rehash来优化。
3. **哈希表的大小**
    - **Redis**：扩容时通常将容量翻倍（2的幂次方）。
    - **Java**：同样使用2的幂次方，以便通过 `(n-1) & hash` 快速定位下标 

总结来说，**原理相通，实现迥异**。Redis 的设计完全服从于高性能（高并发）和单线程特性。

### Q7：ZSet 中 skiplist 和 hashtable 如何配合使用？

**内存结构：**
```
ZSet
├── hashtable
│     "apple"  -> 1.0
│     "banana" -> 2.0
│     "cherry" -> 3.0
│
└── skiplist（按 score 排序）
      [apple:1.0] -> [banana:2.0] -> [cherry:3.0]
```
member 字符串只存一份，两个结构的节点都持有指向它的指针，不重复占内存。

**不同命令走不同结构：**

| 命令 | 走哪个结构 | 复杂度 | 说明 |
|------|------|------|------|
| ZSCORE key member | hashtable | O(1) | 直接查 member 对应的 score |
| ZRANGE key 0 -1 | skiplist | O(logN+M) | 顺序遍历第1层链表 |
| ZRANGEBYSCORE key 0 100 | skiplist | O(logN+M) | 按 score 范围查询 |
| ZRANK key member | skiplist | O(logN) | 按 score 排序后的排名 |
| ZADD key score member | 两个都更新 | O(logN) | 见下方详细说明 |
| ZREM key member | 两个都删除 | O(logN) | hashtable 删 key，skiplist 找节点删除 |

**ZADD 的两种场景：**

新增（member 不存在）：
```
1. hashtable 插入 "apple" -> 1.0
2. skiplist 插入 apple:1.0 节点
```

更新（member 已存在，score 变了）：
```
ZADD key 5.0 "apple"（原来是 1.0）
1. hashtable 查到旧 score = 1.0
2. hashtable 更新 "apple" -> 5.0
3. skiplist 找到 apple:1.0 节点删除
4. skiplist 按新 score 重新插入 apple:5.0
```
score 变了排序位置就变了，skiplist 无法原地修改，必须先删再插。hashtable 的核心价值就在这里——O(1) 查到旧 score，才能定位 skiplist 旧节点。

**为什么不能只用一个：**
```
只用 hashtable：无序，ZRANGE 范围查询无法实现
只用 skiplist： ZSCORE 点查 O(logN)，且 ZADD 更新时无法 O(1) 找到旧节点
```
代价是写操作需要同时维护两个结构，但读性能两全其美。

**一句话总结：hashtable 无序但查询快 O(1)，skiplist 有序但查询慢 O(logN)，两者互补缺一不可。**

### Q7.1：跳表的插入和删除过程？

**插入（以插入 score=2.5 为例）：**

1. **找前驱**：从最高层往下，找到每层中比 2.5 小的最后一个节点并记录
```
层3：记录 head
层2：记录 banana(2.0)
层1：记录 banana(2.0)
```
2. **随机层数**：随机决定新节点有几层（每层概率约 50%，期望 O(logN) 层）
3. **更新指针**：将前驱节点指向新节点，新节点指向原后继
```
层2：banana(2.0) -> 新节点(2.5) -> cherry(3.0)
层1：banana(2.0) -> 新节点(2.5) -> cherry(3.0)
```

**删除：**

1. **找前驱**：同插入，从最高层往下找目标节点，记录每层前驱
2. **逐层摘除**：将前驱节点指针直接指向目标节点的下一个节点
```
层2：banana(2.0) -> cherry(3.0)  // 跳过被删节点
层1：banana(2.0) -> cherry(3.0)
```
3. 释放内存

**核心：两者都依赖"找前驱"这一步，本质就是一次跳表查找，O(logN)。**
```
插入：找前驱 → 随机层数 → 更新指针   O(logN)
删除：找前驱 → 逐层摘除 → 释放内存   O(logN)
```

### Q7.2：跳表和 B+ 树的核心差异？MySQL 为什么用 B+ 树，Redis 为什么用跳表？

核心差异就一个：**磁盘 IO vs 内存随机访问**。

**MySQL 不能用跳表：**
跳表节点随机分散在内存各处，范围查询跟着指针到处跳，每跳一次就是一次随机磁盘 IO，在磁盘场景下灾难性的慢。B+ 树节点对齐磁盘页（16KB），叶子节点物理连续，范围查询顺序读磁盘，利用预读，IO 次数极少。

**Redis 不需要用 B+ 树：**
Redis 数据全在内存，随机访问几乎无代价，跳表的随机指针跳跃不是问题。B+ 树插入可能触发节点分裂，维护平衡复杂，实现成本高，在内存场景下收益不大。跳表插入只需随机生成层数，实现简单且性能够用。

| | B+ 树 | 跳表 |
|------|------|------|
| 设计目标 | 磁盘存储，减少 IO | 内存存储，实现简单 |
| 节点结构 | 对齐磁盘页，扇出大，树矮 | 随机层数，链表结构 |
| 范围查询 | 叶子链表顺序扫描，顺序 IO | 第1层链表顺序扫描，内存随机访问 |
| 插入维护 | 可能触发节点分裂，复杂 | 随机层数，无需平衡，简单 |

**一句话：跳表放磁盘 → 随机 IO 爆炸；B+ 树放内存 → 实现复杂但收益不大。**

### Q8：List （链表）的 quicklist 是什么结构？

列表使用 快速链表（quicklist）数据结构存储，而快速链表就是 双向链表 与 压缩列表 的组合。

quicklist = 双向链表 + 每个节点是一个 listpack（压缩列表）。

- 解决了纯链表内存碎片多的问题
- 解决了纯 listpack 数据量大时插入慢的问题
- 通过 `list-max-listpack-size` 控制每个节点的 listpack 大小


## 底层结构：双向链表

前节点、后节点、值。

![[Pasted image 20260422204520.png]]
redis在链表的基础上，又封装了一层结构：
list 结构为链表提供了链表头指针 head（取头结点快，头结点可以指向null）、链表尾节点 tail（取尾结点快，未节点可以指向null）、链表节点数量 len（取长度快）、以及可以自定义实现的 dup、free、match 函数。
![[Pasted image 20260422205523.png]]

缺陷：链表的缺陷也是有的，链表每个节点之间的内存都是不连续的，意味着无法很好利用 CPU 缓存。能很好使用缓存的是：数组，这个东西在缓存里面是连续的。


## 底层结构：压缩列表
注意是列表，一个连续的内存区域。
通过不同的划分，划分出很多块儿，每一块都有自己的作用。
![[Pasted image 20260422233313.png]]

第一块：保存整个列表的字节占用（一共多大）
第二块：收尾偏移量，能快速定位尾节点的位置（尾结点在哪儿）
第三块：整个空间包含的节点数量（一共多少）
第四块：标记结束
中间：真正保存数据的内容
第一部分：前一个元素多大（要么1个字节，要么5个字节，有连锁更新的问题）
第二部分：当前元素数据类型、占用内存空间
第三部分：真实的数据

问题1：查找头尾和大小好查，查中间需要遍历
问题2：连锁更新，每一块存储前一个元素多大的部分，更新了。
过程：头插了一个新元素，长度超过254，后面第二个元素需要用5个字节
![[Pasted image 20260422233736.png]]

因此：压缩列表只会使用在：**保存的节点数量不多的场景**


## 底层结构：快速链表
快速链表 = 压缩链表 + 双向链表。每一个双向链表的node节点不再保存整数或者字节数组，而是保存一个压缩列表。

### Q9：Set 的特点是什么？底层如何实现去重？

Set 核心特点：**无序、不重复**。

**底层三种结构及去重方式：**

| 结构 | 触发条件 | 去重方式 | 复杂度 |
|------|------|------|------|
| intset | 全是整数 且数量 ≤ 512 | 二分查找，找到相同值不插入 | O(logN) |
| listpack | 含非整数 且数量少（≤ 128） | 遍历所有元素，找到相同值不插入 | O(N) |
| hashtable | 超过阈值 | 计算 hash 定位桶，遍历链表检查是否存在 | O(1) |

**切换路径：**
```
全整数 + 少量  →  intset
含字符串 + 少量 →  listpack
超过阈值       →  hashtable
```

**本质：Set 复用了 hashtable，但只用了 key 部分，value 是空占位（NULL）。** Set 里的元素在 hashtable 中作为 key 存储，去重靠的是 key 的唯一性，不是遍历 value。intset 是 Set 特有的结构，专为纯整数集合优化，其他类型没有。

### Q10：各类型底层结构为什么会切换？切换的根本原因是什么？

**根本原因：数据量小时省内存优先，数据量大时性能优先。**

listpack 是紧凑连续内存，无任何索引，查找是 O(N)。数据量少时 O(N) 的绝对耗时可接受，内存利用率高；数据量大时 O(N) 不可接受，必须升级到有索引的结构。

```
数据量小 → listpack（连续内存，无指针开销，省内存，O(N) 可接受）
数据量大 → 有索引的结构（hashtable O(1)、skiplist O(logN)，性能优先）
```

**各类型切换汇总：**

| 类型 | 小数据结构 | 触发条件 | 大数据结构 | 原因 |
|------|------|------|------|------|
| String | int / embstr | 长度 > 44 字节 | raw SDS | 短字符串对象头+SDS连续分配，省一次 malloc |
| Hash | listpack | 元素 > 128 或 value > 64B | hashtable | O(N) 查找不可接受，换 O(1) |
| List | - | 始终 | quicklist | 3.2 后统一，listpack 节点限制大小平衡内存和性能 |
| Set | intset（纯整数）/ listpack | 元素 > 512 或含非整数 | hashtable | intset 二分 O(logN)，超阈值换 O(1) |
| ZSet | listpack | 元素 > 128 或 member > 64B | skiplist + hashtable | 需要同时支持 O(logN) 范围查和 O(1) 点查 |

**listpack 是"穷人版"结构**——没有任何索引，靠遍历工作，只在数据量小时有意义。一旦超过阈值，升级到有索引的结构是必然选择。

### Q11：为什么 Redis 是单线程却还这么快？

1. **纯内存操作**：数据全在内存，读写极快
2. **单线程避免锁竞争**：无上下文切换和加锁开销
3. **IO 多路复用**：epoll 监听多个连接，单线程处理大量并发请求
4. **高效数据结构**：针对不同场景选用最优底层结构
