# Redis 性能问题

## 大 key 问题

**什么是大 key：**

本质是单个 key 对应的数据量太大，但不同类型原因不同：
```
String：value 本身太大（超过 10KB）
  key → 一个很大的字符串/JSON/二进制

Hash/Set/ZSet/List：元素数量太多（超过 5000）
  key → {field1:v1, field2:v2, ... field100000:v100000}
  单个 field 的 value 可能不大，但元素太多导致整体数据量大
```

**危害：**
```
1. 内存不均衡：Cluster 下大 key 所在节点内存远高于其他节点
2. 阻塞主线程：删除大 key 时 DEL 是同步操作，元素多时耗时长，阻塞其他请求
3. 网络传输慢：读取大 key 占用大量带宽，影响其他请求
```

**解决方案：**

拆分大 key：
```
hash_big → hash_1, hash_2, hash_3...
把一个大 key 拆成多个小 key 分散存储
```

删除大 key 用 UNLINK 而不是 DEL：
```
DEL：同步删除，阻塞主线程
UNLINK：异步删除，把删除任务交给后台线程，主线程不阻塞
```

## 热 key 问题

**什么是热 key：**
某个 key 访问频率极高，大量请求集中打到同一个节点。
```
比如：热点新闻 → 瞬间百万请求都访问同一个 key
→ 该节点 CPU 打满，其他节点闲置
→ 单节点成为瓶颈
```

**解决方案：**

方案一：**本地缓存**
```
在应用服务器本地缓存热 key
请求先查本地缓存，命中直接返回，不请求 Redis
→ 大幅减少 Redis 请求量
缺点：本地缓存和 Redis 数据一致性问题
```

方案二：**key 复制**
```
把热 key 复制成多份：
hot_key_1, hot_key_2, hot_key_3...
读取时随机选一个：hot_key_{random(1,3)}
→ 请求分散到多个节点
```

方案三：**集群扩容**
```
增加 Cluster 节点，把热 key 所在 slot 迁移到新节点
分散压力
```

---

## 大 key vs 热 key

```
大 key：单个 key 的数据量太大，影响内存和操作耗时
热 key：单个 key 的访问频率太高，影响节点 CPU 和带宽
两者可以同时存在，也可以独立出现
```
